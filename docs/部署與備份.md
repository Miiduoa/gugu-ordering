# 部署、啟動與備份

## 目前交付狀態

已提供可執行程式、單檔互動展示、測試與部署設定。沒有購買主機、網域、簡訊額度，也沒有建立店家的公開正式點餐網址。Docker／Caddy 設定檔在此環境未實際建置部署，需在目標主機驗證。不要把本機網址或測試展示當成正式上線。

## 本機 Python

最簡單是 README 的 `bash start.command`。手動啟動如下：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python manage.py setup
.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1 --no-proxy-headers
```

需要 Python 3.11 以上。資料保存在 `data/`，請放在本機一般資料夾，不放在會自動同步的 iCloud／Dropbox／NAS 目錄。`.venv` 不含在交付包，首次安裝需要網路。不要搬動執行中的 SQLite 檔案。

忘記密碼：停止使用該帳號後在主機執行 `python manage.py reset-password --username owner`。只有能操作主機的人能重設管理者，不透過公開網頁顯示或寄送舊密碼。

## Docker 本機展示

需先自行安裝 Docker 與 Compose；此版本未在交付環境驗證 Docker build。

```bash
docker compose up -d --build
docker compose exec app python manage.py setup
docker compose logs -f app
```

`compose.yml` 只在本機 127.0.0.1 暴露 8000 port，資料保存在 `gugu-demo` 專案的命名 volume。`docker compose down` 不刪除 volume；**不要執行 `down -v`**，那會連資料刪掉。

## 正式單店部署

先取得店家授權，由店家確認菜單、自取售價、規格、營業時段、庫存、接單人員與現金／退款流程。使用店家可持續負擔且有人管理的 Linux 主機，並準備一個由店家控制的網域。主機及網域費用取決於實際選擇；本交付沒有代訂服務或承諾免費營運。

將 `DOMAIN` 指向正式主機，允許 80／443 對外。應用的 8000 port 不對外暴露。複製並編輯 `.env.live.example` 為 `.env.live`，把示意網域改成自己真正控制的網域。然後：

```bash
docker compose --env-file .env.live -f compose.live.yml config
docker compose --env-file .env.live -f compose.live.yml up -d --build
docker compose --env-file .env.live -f compose.live.yml exec app python manage.py setup
```

`compose.live.yml` 會使用獨立 `live-data`，不載入範例菜單。HTTPS 由 Caddy 處理，cookie 設為 Secure。首次憑證核發仍取決於網域解析與主機對外連線；請檢查 Caddy 的日誌，不要先宣稱已啟用。

應用信任的反向代理固定為 `10.89.0.2`。若此網段與主機既有網路衝突，需一起更改 Compose 網段、容器 IP 與 `--forwarded-allow-ips`。不要放寬成信任所有來源，否則攻擊者可能偽造來源 IP 影響限流。

登入後先更改管理者密碼，再建立每位店員的帳號。建立正式菜單，移除不供應的規格與任何未確認文字。設定每日庫存、營業時間、公休與容量，確認無誤才勾選「已確認正式資料」。新 live 資料庫在沒有菜單、未完成確認、休息中或暫停接單時不接單。

**不得把 demo 資料庫改成 live。** 程式以 installation 記錄阻擋環境混用。正式資料只能從新的目錄／volume 開始；不要刪掉這項保護來省事。

健康檢查與驗收：

```bash
docker compose --env-file .env.live -f compose.live.yml exec app python manage.py check
docker compose --env-file .env.live -f compose.live.yml logs --tail=100 app caddy
```

用店外手機的行動網路實測點餐、店家另一台裝置接單、查詢更新、正確現金紀錄與取餐，再用少量真實試營運確認。人工確認庫存、出餐容量與現金全部能對上，才張貼公開 QR Code。請勿把店家顧客當開發測試資料。

## 備份

主機上的 SQLite 使用線上備份 API，不以複製執行中檔案代替：

```bash
.venv/bin/python manage.py backup
.venv/bin/python scripts/backup_rotate.py
```

第二個命令會先維護匿名化，再建立完整性檢查通過的備份，並刪除同資料夾 7 天以前的 `gugu-*.sqlite3`。可用 `BACKUP_KEEP_DAYS` 設為 1–30 天。此腳本不會自動上傳或加密；主機檔案權限不是加密。需要依店家的資料政策另外配置加密磁碟／加密異地備份，且異地副本也要輪替刪除。

正式 Docker 執行：

```bash
docker compose --env-file .env.live -f compose.live.yml exec -T app python scripts/backup_rotate.py
```

可由主機排程每天關店後呼叫；**排程不會自行安裝**。排程時間依主機時區，不應直接假設是台灣時間。排程需收集失敗通知，定期檢查備份大小與完整性。若需要更低可接受資料遺失量，增加備份頻率；每天一次備份在最壞情況可能失去接近一天的新單。

資料庫與持久化密鑰 `data/.secret` 必須一起安全備份。主機環境以 SECRET_KEY 設定的情況，則另外保管該密鑰；不要提交到 GitHub。不要把真實密碼、聯絡資料或備份附件傳進公開 issue。

## 還原

還原會覆蓋資料，是維運作業，不能在店家營業接單中隨便執行。先暫停接單、停止伺服器，保留事故時資料庫的另一份副本，再使用要還原的同環境備份。CLI 的 `--confirm` 是人工確認，不會神奇地保證另一個程序沒有連線；操作人員必須確實停止服務。

```bash
# Python 方式：先在原終端機 Control+C 停止
.venv/bin/python manage.py restore --file /完整路徑/備份.sqlite3 --confirm
.venv/bin/python manage.py maintenance
.venv/bin/python manage.py check
```

Docker：先 `stop app`，再用一次性 `run --rm --no-deps app` 容器執行還原（指向 volume 內確實存在的備份路徑），完成檢查後再 `up -d app`。還原程式會檢查完整性、schema version、環境類型並撤銷所有登入。

舊備份可能含尚未匿名化的資料，還原後要先執行 maintenance。核對備份時間後曾收款／退現金／交付的所有訂單，不能只看畫面就再次收款或再次交餐。預設方案不是高可用、多機切換或零資料遺失系統。

## 不能省略的維運

監控主機磁碟、HTTPS 到期／憑證錯誤、API health、備份失敗及服務重啟。作業系統與套件需定期更新，更新前在測試副本驗證。本包釘選的是已測試版本，不是「永遠安全」的版本。
